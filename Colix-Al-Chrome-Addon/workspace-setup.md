# Clonix Workspace Setup

This document contains the database setup, migration order, Supabase Auth requirements, RLS expectations, and rollout checks for invitations and shared Clonix resources.

## 1. Prerequisites

1. Enable Supabase Auth and configure Google OAuth.
2. Configure the invitation email provider and deploy the acceptance function.
3. Choose an email provider such as Resend or Postmark.
4. Store the provider key only as an Edge Function secret. Never place it in the extension.
5. Review and apply the workspace additions in `src/db.sql` in a staging project first. The schema uses idempotent creation for existing tables, but inspect every migration before production.

The extension uses Chrome Identity to obtain the user's Gmail address. Supabase Google OAuth and passwords are not used. Workspace operations go through Edge Functions, which validate the Gmail address against the `users` table and workspace membership before using the service role key server-side.

The extension excludes Google and Supabase domains from content-script injection so the text-expander code cannot interfere with OAuth provider pages.

If `folders` or another legacy table already exists, do not run its original `CREATE TABLE` statement separately. Use the current `db.sql`, which uses `CREATE TABLE IF NOT EXISTS` for the existing folders table, and run the workspace `ALTER TABLE`, indexes, functions, and policies after reviewing them.

## 2. Schema and migration order

The schema adds `workspaces`, `workspace_members`, `workspace_invitations`, `resource_permissions`, an `auth_user_id` bridge on `users`, and `workspace_id` columns on existing folders, shortcuts, and forms.

Run this migration after the new tables exist:

```sql
INSERT INTO public.workspaces (name, owner_id)
SELECT COALESCE(NULLIF(TRIM(first_name || ' ' || last_name), ''), split_part(email, '@', 1) || '''s Workspace'), id
FROM public.users u
WHERE NOT EXISTS (SELECT 1 FROM public.workspaces w WHERE w.owner_id = u.id);

INSERT INTO public.workspace_members (workspace_id, user_id, role)
SELECT w.id, w.owner_id, 'owner' FROM public.workspaces w
WHERE NOT EXISTS (SELECT 1 FROM public.workspace_members m WHERE m.workspace_id = w.id AND m.user_id = w.owner_id);

UPDATE public.folders f SET workspace_id = w.id FROM public.workspaces w
WHERE f.workspace_id IS NULL AND w.owner_id = f.user_id;
UPDATE public.shortcuts s SET workspace_id = w.id FROM public.workspaces w
WHERE s.workspace_id IS NULL AND w.owner_id = s.user_id;
UPDATE public.forms f SET workspace_id = w.id FROM public.workspaces w
WHERE f.workspace_id IS NULL AND w.owner_id = f.user_id;
```

After a user signs in with Supabase Auth, link the Auth user to the existing application user by normalized email. Run this as a privileged migration or protected server operation, not from the extension:

```sql
UPDATE public.users app_user
SET auth_user_id = auth_user.id
FROM auth.users auth_user
WHERE app_user.auth_user_id IS NULL
	AND lower(app_user.email) = lower(auth_user.email);
```

The `auth_user_id` bridge is required because the legacy `users.id` values were generated by the application and are not automatically equal to `auth.uid()`.

After OAuth succeeds, the extension automatically fills `users.auth_user_id` for the matching email. If Google authorization fails before the callback, verify both redirect settings before testing Workspace again.

After verification, make `workspace_id` `NOT NULL` in a later migration. Existing IDs and content are preserved.

## 3. Auth and API setup

The client obtains the Gmail address from Chrome Identity and sends it to workspace Edge Functions as `x-user-email`. Functions perform all workspace authorization and database access. Invitation links are the proof that the invited person controls the mailbox.

Invitation creation and acceptance must be implemented as Edge Functions or protected RPCs. The invite function validates owner/admin permission, normalizes email, hashes a random token, creates the invitation, and sends the email. The accept function validates token, expiry, status, and authenticated email before inserting membership.

## 4. RLS rules

The helper functions and baseline policies are included in `src/db.sql`. Add resource policies for each existing table before production:

- Members can read resources belonging to their workspace.
- Viewers can read/use shared resources but cannot update or delete them.
- Editors can update resources with effective `edit` permission.
- Owners/admins can manage members, invitations, and permissions.
- Invitation tokens are never exposed to ordinary members.
- Removed members lose access immediately.

Test owner, admin, editor, viewer, removed-member, and unrelated-user sessions. Do not rely on manually supplied email headers.

## 5. Sharing behavior

Folder sharing is the first supported workflow. A folder permission applies to child snippets and forms. New children inherit the folder workspace and access. Individual permissions can provide exceptions. Resources remain owned by the workspace and are not copied into a subuser's personal collection.

## 6. Sync rollout

Keep legacy personal sync during migration. Then update the sync manager to select by active `workspace_id` or an authorized view/RPC, include effective permission locally, namespace storage by account/workspace, reject queued writes after revocation, use server `updated_at` for last-write-wins, and never delete shared resources without permission.

Remove `x-user-email` authorization only after authenticated workspace sync passes staging tests.

## 7. Workspace UI

The workspace page currently provides a visual UI only. Invitation, membership loading, revocation, email delivery, and workspace APIs are intentionally disabled until a future backend implementation is added.

## 8. Verification checklist

- Existing users retain personal data after migration.
- Unrelated users cannot read another workspace.
- Viewer writes are rejected by RLS.
- Removed members lose access immediately.
- Invitation tokens expire and cannot be reused.
- Invitations cannot be accepted by another email address.
- Revoked invitations cannot be accepted.
- Shared folder children appear after sync.
- Workspace switching cannot show stale local data.
- Pending writes cannot overwrite resources after permission removal.
